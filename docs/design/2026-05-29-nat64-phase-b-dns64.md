# NAT64 Phase B — DNS64 in MagicDNS (2026-05-29)

Second phase of the NAT64 / IPv6 dual-stack umbrella
(`docs/design/2026-05-27-nat64-architecture.md`). Adds the DNS64
synthesis capability — and the per-tenant configuration that gates it —
so an IPv6-only query for an IPv4-only destination can be answered with
a synthetic AAAA in the configured NAT64 prefix. This phase is a
**forward-looking enabler**: it wires the resolver and the config
surface, but the synthesized AAAA points into a prefix that nothing
routes until Phase C (the translator) ships. It is shipped **off by
default**, per-tenant, so existing meshes see zero behaviour change.

## 1. Scope

- **Controller:** activate `tenants.nat64_prefix` (the Phase A hook
  column) with API-edge validation; add `tenants.dns64_enabled`
  (default false); push both to clients on register; teach the
  route-conflict checker that `<nat64_prefix>::/96 → egress` is a
  synthesised route (umbrella §5 hook).
- **Synthesis primitive:** a pure `v4 + /96 prefix → v6` function
  (RFC 6052 §2.2), implemented + tested on both the Go (controller)
  and Swift (Apple) sides.
- **Apple resolver:** external-name DNS64 in the `NEDNSProxyProvider` —
  when DNS64 is enabled and an external name has an A record but no
  AAAA, synthesise an AAAA in the NAT64 prefix. Gated by the per-tenant
  flag; off ⇒ pure passthrough (today's behaviour).

The phase ends when: a tenant admin can set a (validated) NAT64 prefix
and flip `dns64_enabled`; a client receives both on register; and an
Apple client with the flag on synthesises a DNS64 AAAA for an external
IPv4-only name (verified by `dig`, even though the address black-holes
until Phase C).

## 2. Out of scope (Phase B)

- **Linux / CLI DNS path.** The CLI has no DNS interception today
  (no resolver, no `NEDNSProxyProvider` equivalent). Building one
  (resolv.conf takeover / a stub resolver / systemd-resolved
  integration) is substantial net-new work that contradicts the
  enabler framing. The umbrella's "Apple and Linux kept in lockstep"
  goal is **deferred** — Linux DNS64 is a later phase (likely folded
  into Phase C, where a real egress/translator gives it a consumer).
- **The 6→4 packet rewrite** (Phase C translator). Phase B's
  synthesised AAAA black-holes until then; accepted.
- **HCL IPv6 literals / observability labels** (Phase D).
- **Web UI** for the two tenant settings. Phase B exposes them on the
  controller admin API + register push only; a Web toggle is a small
  deferred follow-up.
- **RFC 6147 special-range exclusions** beyond loopback/link-local
  (e.g. RFC 1918 filtering) — deferred to Phase C/D when egress
  reachability is real.

## 3. Dependencies & sequencing

Phase B's controller work builds directly on Phase A:

- `tenants.nat64_prefix` is added by **migration 00018** (Phase A
  PR #232) — Phase B *activates* it, it does not create it.
- Phase B adds **migration 00019** (`tenants.dns64_enabled`), which
  must be numbered after 00018.
- The register-response push extends the proto `RegisterResponse`
  introduced/extended across Phase A PRs.

Therefore Phase B implementation **must stack on the Phase A stack
(#232 → #233 → #234) or wait for it to merge to main.** The migration
number and the proto field numbers are assigned against post-Phase-A
state. This spec can be written and reviewed independently; the code
cannot land before #232.

## 4. Cross-phase decisions inherited (locked in umbrella §4)

- NAT64 prefix default `64:ff9b::/96` (RFC 6052 well-known). Per-tenant
  override via `tenants.nat64_prefix`. Must be exactly `/96`.
- DNS64 synthesis embeds the 32-bit IPv4 into the low 32 bits of the
  `/96` (RFC 6052 §2.2 — for a `/96`, the v4 occupies bits 96–127, the
  trailing 32 bits, with no `u`-byte gap). For `64:ff9b::/96` and
  `93.184.216.34`: `64:ff9b::5db8:d822`.
- DNS64 is **per-tenant policy**, controller-pushed — mirrors the
  Tailscale per-tailnet model. Resolution of *which* names get
  synthesised is by the "no native AAAA" rule (RFC 6147), not by
  literal address matching.

## 5. Schema migration — `00019_tenant_dns64.sql`

```sql
-- +goose Up
-- +goose StatementBegin

-- NAT64 Phase B — per-tenant DNS64 enable flag. nat64_prefix already
-- exists (migration 00018, Phase A hook). Default false so existing
-- tenants see no behaviour change; an admin opts in once Phase C makes
-- the synthesised prefix routable.
ALTER TABLE tenants ADD COLUMN dns64_enabled BOOLEAN NOT NULL DEFAULT false;

-- +goose StatementEnd

-- +goose Down
-- +goose StatementBegin

ALTER TABLE tenants DROP COLUMN IF EXISTS dns64_enabled;

-- +goose StatementEnd
```

No backfill: the safe default is `false`, and `nat64_prefix` already
defaults to NULL (interpreted as the well-known `64:ff9b::/96`).

## 6. `internal/nat64` package (Go)

New package so the prefix logic stays single-purpose and testable,
mirroring the Phase A `ipalloc/v6map` precedent.

```go
// DefaultPrefix is the RFC 6052 well-known NAT64 prefix, used when a
// tenant has not set nat64_prefix.
const DefaultPrefix = "64:ff9b::/96"

// ParsePrefix validates a tenant nat64_prefix string. It must be a
// well-formed /96. Empty returns the DefaultPrefix. Anything else is
// an error (surfaced as 400 at the API edge).
func ParsePrefix(s string) (netip.Prefix, error)

// Synthesize embeds a 32-bit IPv4 into the low 32 bits of a /96 NAT64
// prefix (RFC 6052 §2.2). prefix must be a /96; v4 must be a 4-byte
// address. e.g. Synthesize(64:ff9b::/96, 93.184.216.34) =
// 64:ff9b::5db8:d822.
func Synthesize(prefix netip.Prefix, v4 netip.Addr) netip.Addr
```

Tests: `ParsePrefix` accepts `64:ff9b::/96` and a custom `/96`, rejects
`/64`/`/128`/malformed/non-v6, and maps empty → default. `Synthesize`
round-trips a representative v4 set incl. boundaries; a known-vector
test pins `64:ff9b::/96 + 93.184.216.34 = 64:ff9b::5db8:d822`.

## 7. Controller — config surface + register push

- **Tenant admin API:** extend the existing tenant-settings path so an
  admin can read and write `nat64_prefix` (validated via
  `nat64.ParsePrefix`; 400 on a non-`/96`) and `dns64_enabled`. Follow
  the established admin tenant API + audit-log pattern.
- **Repo:** `Tenant` gains `NAT64Prefix string` (text, `""` ⇒ default)
  and `DNS64Enabled bool`; SELECT/RETURNING/Scan paths updated (same
  shape as the Phase A `IP6Pool` addition).
- **proto:** `RegisterResponse` gains `bool dns64_enabled` and
  `string nat64_prefix` (the resolved prefix, i.e. the well-known
  default substituted when the column is NULL, so the client never has
  to know the default). Empty/false on a legacy controller ⇒ client
  leaves DNS64 off.
- **route-conflict checker** (`internal/routes/conflicts.go`): treat
  `<resolved nat64_prefix>::/96` advertised by an egress peer as a
  synthesised route, so a future Phase C egress advertising it does not
  trip a false-positive conflict. Tests assert no conflict is reported
  for the NAT64 prefix route.

## 8. Apple resolver — external-name DNS64

The `NEDNSProxyProvider` already forwards non-`.bamboo` queries
upstream untouched. Phase B adds a DNS64 path, gated by the
controller-pushed `dns64_enabled` flag (stored client-side from the
register response):

**When `dns64_enabled == false`:** unchanged — pure passthrough +
existing `.bamboo` synthesis. No new behaviour.

**When `dns64_enabled == true`, for an external (non-`.bamboo`) AAAA
query:**
1. Forward the AAAA query upstream.
2. If upstream returns a native AAAA → return it unchanged (RFC 6147:
   prefer native; never synthesise when a real AAAA exists).
3. If upstream returns NOERROR/empty (NODATA) for AAAA → issue an A
   query upstream for the same name.
4. For each returned A record, synthesise an AAAA = `nat64.Synthesize(
   prefix, a)` and return them as the AAAA answer (TTL copied from the
   A answer).
5. Exclude loopback/link-local A answers from synthesis; pass the
   (empty) AAAA through if no synthesisable A remains.

**`.bamboo` path unchanged** — Phase A already returns the peer's
native `ip6` for `.bamboo` AAAA queries; no peer lacks an `ip6`
post-Phase-A, so there is no intra-mesh DNS64 surface.

**Where the I/O lives:** the upstream A-query + correlation is
orchestrated in the provider/flow layer (it already proxies upstream);
the synthesis itself is the pure Swift `nat64Synthesize` function. The
synthesis function is unit-tested; the provider orchestration is
verified by compile (`CODE_SIGNING_ALLOWED=NO`, since
`NEDNSProxyProvider` cannot link into the `AppleSharedTests` xctest
bundle) + manual E2E.

## 9. Error / edge cases

- **Malformed `nat64_prefix`** — rejected at the API edge (400); never
  reaches a client. The resolved prefix pushed on register is always a
  valid `/96`.
- **`dns64_enabled` true but `nat64_prefix` NULL** — fine: the resolver
  uses the well-known `64:ff9b::/96` (the controller resolves NULL →
  default before pushing).
- **Black hole until Phase C** — a synthesised `64:ff9b::<v4>` AAAA has
  no route until an egress translator exists. This is why the default
  is off and the flag is per-tenant admin-controlled. Documented as
  expected; the admin flips it on as part of Phase C bring-up.
- **Native AAAA present** — never synthesise (step 2). Prevents
  hijacking dual-stack names.
- **Legacy controller (no dns64 fields)** — client sees false/empty ⇒
  DNS64 stays off; pure passthrough.

## 10. Test plan

- `internal/nat64` — `ParsePrefix` accept/reject/default table;
  `Synthesize` round-trip + known vector (`64:ff9b::5db8:d822`).
- Tenant API — set valid `/96` (200 + persisted), non-`/96` (400),
  toggle `dns64_enabled`; register response carries resolved prefix +
  flag.
- route-conflict — a NAT64-prefix `/96` route from an egress peer
  reports no conflict.
- Swift `nat64Synthesize` — unit test mirroring the Go known vector.
- Apple resolver — compile-verified; manual E2E: flag on,
  `dig AAAA <ipv4-only-name>` through the proxy returns
  `<prefix>::<v4>`; native-AAAA name returns the real AAAA; flag off
  returns upstream untouched; `.bamboo` unchanged.

## 11. PR breakdown (≈2)

1. **Controller — config + push + synthesis primitive.** Migration
   00019; `internal/nat64` (validate + synthesize + tests); `Tenant`
   repo fields; tenant admin API read/write with validation; proto
   `RegisterResponse.dns64_enabled` + `nat64_prefix` + register push;
   route-conflict awareness. All backend + unit tested.
2. **Apple — external DNS64 resolver path.** Swift `nat64Synthesize`
   + tests; `NEDNSProxyProvider` external DNS64 (upstream A-query +
   synthesise), gated by the pushed flag, default off; compile +
   manual E2E.

## 12. Phase boundary

Phase B delivers the resolver and config halves. Phase C (translator on
admin-designated egress peers) makes the synthesised prefix routable
and is what turns DNS64 from an enabler into a live capability. The
Phase C hooks (`peers.nat64_egress_capable`, `nat64_egress_approved`)
already exist in schema from Phase A migration 00018.

# NAT64 Phase C1 — PR 2 (CLI flag + Web approval toggle) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give operators the two human-facing surfaces for the C1 egress feature — a CLI `--advertise-nat64-egress` flag so a peer self-advertises as a NAT64 egress candidate, and a Web admin toggle to approve it — both mirroring the shipped exit-node UX.

**Architecture:** PR 1 (#238) added the controller half: the REST register body accepts `advertiseNat64Egress`, `POST /api/v1/peers/{id}/nat64-egress` flips approval, and `/api/v1/peers` JSON carries `nat64EgressCapable`/`nat64EgressApproved`. PR 2 wires the clients. The CLI mirrors `--advertise-exit-node` (a persistent bool flag threaded into the REST register body). The Web mirrors the exit-node approval row in `PeerDrawer` (domain type field → API DTO + mapper → a server action POSTing to the new route → a capability-gated toggle component + i18n).

**Tech Stack:** Go (clients/cli, cobra), TypeScript/React + next-intl (apps/web).

**Spec:** `docs/design/2026-05-30-nat64-phase-c1-egress-acl.md` §7 (CLI) + §8 (Web).

**⚠️ Stacking:** this branch is stacked on **C1 PR 1 (#238)** — it consumes the controller's `advertiseNat64Egress` register field + the `/nat64-egress` approval route + the `nat64EgressCapable/Approved` JSON fields. PR base is `feat-nat64-phase-c1-egress`. It cannot merge before #238.

**Verification note:** `apps/web` has no unit-test runner — Web is verified by `make web-lint` (`next lint` + `tsc --noEmit`). The CLI has no test for the register body today; verify with `go build` + `go vet` + any existing `go test ./clients/cli/...`.
